## 动手前

先把仓库里已有的文档全读一遍，当作这次工作的输入：
`README.md`、`CHANGELOG.md`、`AGENTS.md`，以及 `docs/` 下的设计/工程/状态/接口/运维文档。
要做的是「重新理解 + 合并 + 升版」，不是新建、更不是覆盖。

## 摸清这些

1. **技术栈与版本** —— 读 `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle`
2. **目录结构** —— 各目录干嘛用、入口文件在哪、模块边界在哪
3. **怎么跑** —— 装依赖、启动、构建、测试、lint 的**确切命令**（从 `package.json` 的 scripts / `Makefile` / CI 配置里找，不要猜）
4. **代码约定** —— 命名、缩进、提交信息格式、分支模型（从现有代码与 `.editorconfig` / `.prettierrc` / 已有提交里读）
5. **不能碰的东西** —— 生成物、密钥文件、`vendor` 目录、大体积资源

## 产出：按标准补齐这套文档

标准见全局规则的「项目文档」段，落到文档上是这些：

| 文档 | 回答什么问题 | 必备 |
| --- | --- | --- |
| `README.md` | 这是什么、怎么装、怎么跑、第一个例子 | 是 |
| `CHANGELOG.md` | 每个版本改了什么、为什么 | 是 |
| `AGENTS.md` | 给 agent 的项目约定（确切命令 / 约定 / 禁区） | 是 |
| `docs/设计.md` | 为什么这么设计、否决了哪些方案、边界 | 有分歧的决策才写 |
| `docs/工程.md` | 构建/测试/发布、目录结构、模块怎么串 | 有新人/流程坑才写 |
| `docs/状态.md` | 现在做到哪、什么能用什么不能、已知问题 | 长周期/多人协作才写 |
| `docs/接口.md` | 对外契约（REST/CLI/配置格式） | 有外部消费者才写 |
| `docs/运维.md` | 部署/回滚、挂了怎么查怎么恢复 | 有生产环境才写 |

- 使用说明可并入 `README.md`
- **缺的文档**：判断这个项目需不需要；需要的**新建**（只写这次真摸到的），不需要的在报告里说明为什么跳过
- **已有的文档**：**逐条过，别整篇覆盖**。仍然成立的保留原文；过期的修正；缺的补上；新增的追加。
  结构可以重排，但原有信息不能丢 —— 某条拿不准还要不要，就保留它，并在聊天里问我
- 文档之间别互相矛盾：同一件事只在一份文档里说，其余的指过去；发现两份对不上，当场指出让我定夺

## 硬要求（这套文档 AI 也要读）

- 只写你**实际读到、验证过**的。拿不准的单独列一节「待确认」，**不要编命令**
- 命令写全：写 `npm run test:unit`，不要写「跑测试」；没实际执行过的命令，后面标「（未验证）」
- 每份文档头带状态/日期或版本号（否则分不清过期文档，会把半年前的命令当现状）
- 设计文档写「为什么 + 否决了哪些方案」，不只写「怎么做」
- 禁区（生成物 / 密钥 / `vendor` / 大文件）单列一节
- 写完在聊天里报告：你读了哪些文件、哪些是沿用旧的、哪些是这次新加或修正的、跳过了哪些文档及原因、还有哪些没搞清
