# 团队基线的问题怎么处理

先判断**这个问题属于谁**，再决定动作。

## 判断

| 问题在哪 | 属于谁 | 怎么办 |
| --- | --- | --- |
| `.pi/git/github.com/kurumi1ksllq/pi-workflow/` 里 | **团队基线**（维护者） | 上报，**别本地改** |
| 项目仓库的 `.pi/settings.json`、`AGENTS.md` | 本项目 | 本地改，正常提交 |
| `~/.pi/agent/` 里 | 个人 | 本地改，随便 |

**为什么团队基线不能本地改**：那份是从 GitHub 克隆的副本，
下次 `pi install` 或删掉重装就没了。你改的东西不会进任何人的环境，也不会被任何人看到。
另外自动更新看到「包目录里有未提交的改动」会**拒绝动手**（终端会提示「没敢动」）——
看到那句就是有人改过包目录：`git -C <包目录> status` 看一眼，不需要就 `git checkout -- .` 还原。

## 上报前先自检：这真的是问题吗

团队基线里有几处**看着别扭但故意的**，别当 bug 报：

| 现象 | 真相 |
| --- | --- |
| `package.json` 的 `version` 和 git tag 不一致 | **以 git tag 为准**。version 字段自 v1.3.0 起已废弃，因为手工同步容易忘 |
| 扩展只在有 `.pi/` 的目录里写 `.mcp.json` | 故意的 —— 基线可以全局安装，不加这道闸会往任何目录塞文件 |
| `team/RULES.md` 不在 `AGENTS.md` 的位置上 | 故意的 —— pi 不加载包内的 AGENTS.md，是扩展读它再注入 |
| `.pi/git/` 里有一堆克隆的包 | 正常，那是安装产物，pi 自带 `.gitignore` 挡住了 |

**拿不准就先问用户**，别直接提 issue。

## 上报方式：收集 + 用户决定，**不要自己提**

发现真问题后：

1. **先告诉用户**发现了什么，并说明这属于团队基线、本地改无效
2. **问用户**要不要提 issue —— 别自己提
3. 用户同意后（且本机有 `gh` 且已认证）：

```bash
gh issue create --repo kurumi1ksllq/pi-workflow \
  --title "<一句话说清问题>" \
  --body "**基线版本**：<注入段里那个 tag>
**现象**：<具体看到什么>
**复现**：<怎么触发>
**期望**：<应该是什么样>"
```

没有 `gh` 或没权限时，把上面这段信息整理好交给用户，让他转给维护者。

## 一次会话最多提一次

同一个问题不要反复提。用户说"先不管"就放下，别追。
