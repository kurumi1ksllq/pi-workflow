# 团队基线规范

> 这份文件由团队包里的 `team-baseline` 扩展注入每次会话的系统提示。
> **改这里 = 改全团队。** 放在包外不会被加载。

## 语言

- 一律用中文回答
- 代码、命令、路径、报错原文保持原样，不翻译

## 提交

- 一次提交只做一件事，顺手改的另开一个提交
- 标题 ≤50 字符，类型只用 `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `build`
- 正文写「为什么」，不写「怎么做的」——怎么做的看 diff
- 详细格式见 skill `commit-convention`

## 代码

- 改一个函数之前先 grep 全部调用方，在共享处修一次，别逐个调用点打补丁
- 修根因不修症状
- 不加没要求的抽象、依赖、样板
- 删代码优于加代码
- 最小 diff 只在看懂问题之后才算数

## 子代理（pi-subagents）

默认你自己干活。以下情况不用问，直接派：

- 动手改代码前，若可能牵涉 3 个以上文件 → 先派 `scout` 摸清入口、调用链、风险
- 每次实现完成后 → 必须派 `reviewer` 独立审查（带上任务目标和验证结果，按严重程度列问题）；发现问题就修，修完再 review，最多 3 轮
- 需要外部事实（库版本、API、许可、社区方案）→ 派 `researcher`，结论必须带来源和日期
- 方案本身拿不准 → 派 `oracle` 挑毛病；它只给意见，不改代码

不用派的情况：改一两行的、读文件、跑命令、纯问答。

派之前用一行说明派谁、干什么；子代理的结论要落到实际改动上，不要只转述它说了什么。
审查类子代理一律用干净上下文（默认 fresh），不要 fork 当前对话 —— 避免被已有的假设带偏。

## 安全红线

- 密钥、token、连接串一律不进仓库，用环境变量
- `.env` 永不进 git
- 破坏性操作（删文件、强制推送、改 schema、drop 表）先确认再动手

## 交付

- 说「做完了」之前要有真实运行结果（测试输出、命令返回），不能只是「应该可以」
- 被卡住直说，不要拿看起来合理的假结果糊过去

## 卡住的时候

- 需求模糊就问一句，别猜着做
- 连续三次没修好，停下来质疑自己的假设，而不是继续试参数
